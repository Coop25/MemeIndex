# MemeIndex second security review — 2026-09-07

The second pass expanded the first review into authentication configuration, authorization, CSRF, uploads, media processing, downstream downloads, restore parsing, background jobs, reel sessions, dependency vulnerabilities, and build context handling. All changes remain local. Production has not been updated.

## Additional findings and disposition

| Priority | Finding and evidence | Disposition |
| --- | --- | --- |
| High, configuration-dependent | Missing OAuth settings silently disabled authentication, and Compose supplied a known example signing key. A deployment using that key would permit token forgery. Tests cover incomplete configuration and example keys; the production secret was not read or tested. | Startup now requires complete auth or explicit anonymous opt-in, rejects short/example signing keys, and Compose no longer supplies a default signing key. |
| High, partially mitigated | mediafetch-go v0.1.10 matches provider names using a substring, so lookalike attacker domains pass its supported-URL check. The application also resolved DNS separately from dialing, and treated redirect-validation errors as success before downloading. | Added application-level DNS-label matching, standard HTTP(S) ports, early provider validation, redirect validation, and connection-time public-IP checks that dial the validated literal. Errors fail closed. Downstream downloader requests still require egress isolation; see remaining work. |
| Medium | A remove-tags-only user could send `action:add` to the suggestion endpoint and add any tag. The regression reproduced HTTP 200 before the patch. | The add action explicitly requires CanAddTags or user-management permission; unauthorized mutation is denied. |
| Medium | State-changing browser requests had no cross-origin protection. A locally simulated same-site sibling origin, carrying a valid cookie, created a share with HTTP 201. SameSite=Lax does not isolate sibling origins. | Go's CrossOriginProtection now wraps all routes. Same-origin share creation and rejection of the sibling-origin request are tested. |
| Medium | Restore validation searched CSV headers for stored_name, but PostgreSQL COPY imports by fixed position. A malicious reordered header could validate a different field from the stored filename actually imported. Imported media/source URLs were also unrestricted. This requires an administrator to import the crafted backup. | Require the exact expected meme CSV column order, canonical /uploads/ paths, and HTTP(S) source URLs. Added regression tests. A malicious archive was not imported into production or a live PostgreSQL database. |
| Medium | FFmpeg/ffprobe parsed uploaded playlists capable of opening referenced media outside the upload directory. An offline container test demonstrated the old ffprobe invocation reading a synthetic referenced MP4 outside that directory. | Allow only self-contained media demuxers and the file protocol. The same integration test confirms playlist rejection and successful ordinary MP4 thumbnail/audio/probe processing. This demonstrates media-file reference access, not arbitrary secret extraction or code execution. |
| Medium | Reel sessions had no user ownership check. Knowing a session ID let another viewer navigate/delete its history; IDs used time-based UUIDv6. | Reel tokens are now HMAC-bound to the current user. New underlying IDs use random UUIDv4. Old/foreign navigation tokens start a fresh reel; foreign deletion tokens fail. |
| Medium | Queued link downloads continued without checking whether the requesting user still had upload permission. | Recheck current permissions before each background retry. Revoked requests are rejected before downloader access. In-flight work is not cancelled by this change. |
| Medium, availability | Multipart parsing had a 256 MiB memory threshold but no total upload cap. JSON, pending login states, archive expansion, and FFmpeg diagnostic output also lacked explicit bounds. | Multipart requests default to 256 MiB total with an 8 MiB memory threshold; normal API bodies are capped at 1 MiB; pending OAuth states at 4,096; backup extraction at 64 GiB and 1,000,000 entries; media diagnostics at 16 KiB and processes at 30 seconds. Added HTTP header/idle timeouts. Tests exercise limits with small fixtures, not production load. |

Additional hardening: authenticated API and OAuth responses now carry private/no-store headers; responses receive nosniff, no-referrer, and frame denial. Secure-cookie configuration cannot be downgraded by a forwarding header. Backslash return paths are rejected defensively; a browser open-redirect exploit was not demonstrated. OAuth transient-cookie deletion headers are now written before the response, rather than deferred until after headers are committed. The Docker build context excludes all data and local test/cache directories.

## Dependency scan

The initial official govulncheck run reported **13 reachable advisories** across the local Go 1.26.2 standard library, pgx v5.7.2, and x/text v0.21.0. Reachability is not proof that the required exploit conditions exist in this application. For example, the pgx SQL advisory requires particular query/protocol conditions; the reviewed application queries use bound parameters.

Updated the minimum Go version and Docker builder to **1.26.6**, pgx to **5.9.2**, x/text to **0.41.0**, x/crypto to **0.56.0**, and x/sync to **0.22.0**. The subsequent `go run golang.org/x/vuln/cmd/govulncheck@v1.7.0 ./...` reported **No vulnerabilities found**. This covers Go dependencies, not the deployed image's FFmpeg, yt-dlp, Debian, PostgreSQL, or Cloudflare components.

Reference advisories: [pgx placeholder confusion](https://pkg.go.dev/vuln/GO-2026-5004), [x/text infinite loop](https://pkg.go.dev/vuln/GO-2026-5970), and [net/url complexity](https://pkg.go.dev/vuln/GO-2026-6218).

## Verification

- `go test ./...`: passing, including the actual-route viewer permission matrix, valid same-origin sharing, denied cross-origin sharing, tag permissions, user-bound reel tokens, revoked background uploads, configuration rejection, archive validation, request-size limits, and pinned remote dialing with mixed/private DNS fixtures.
- `go vet ./...`: passing.
- `node --test scripts/*.test.cjs`: 32 passing tests.
- FFmpeg integration: Linux test binary in the cached MemeIndex development image, with no network, a read-only filesystem, dropped capabilities, and synthetic media in temporary storage. Ordinary MP4 processing passed; a local-reference playlist worked with the old invocation and failed with the restricted invocation.
- The broader Go suite on Windows skips FFmpeg integration if the executables are absent; the isolated Linux run executed that test successfully.
- Source-reviewed SQL construction, metadata HTML sinks, upload filenames, share HMAC validation, user-management boundaries, and archive traversal/link rejection. This does not constitute exhaustive fuzzing or a database concurrency audit.

Read-only production probes for `.env`, `.git/config`, and `data/share_secret` redirected to authentication rather than returning contents. `/api/admin/shares` denied anonymous access. Upload/thumbnail paths denied anonymous access. A spoofed X-Forwarded-Proto did not strip Secure from the production login cookie in the sampled response. No production accounts, stored media, shares, or backups were modified.

## Remaining work before calling this hardened production

1. **Downloader network isolation remains the largest open item.** mediafetch creates additional HTTP clients and invokes yt-dlp, whose subsequent redirects/media requests do not inherit the application's protected transport. Restrict downloader egress to public addresses at the network/proxy boundary and isolate it from PostgreSQL, Ollama, instance metadata, and other private services. Add end-to-end tests against a controlled redirecting fixture. The present patch closes the initial request/lookalike-host paths, not every downstream path.
2. **Verify the production runtime and network boundary.** No access was made to the production host, firewall, tunnel configuration, container settings, or secret store. Compose publishes port 8080 on all interfaces, uses an example database password when unset, and the runtime Dockerfile runs as root. A tunnel does not itself close that published port. Bind appropriately, configure real database credentials, and plan a non-root/container-isolation rollout with correct media-volume ownership.
3. **Resource controls are bounded per request, not a full quota system.** Concurrent downloads/uploads, reel session/history growth, retry queues, expensive database queries, decompression concurrency, and process memory/CPU need per-user/aggregate quotas and container limits. A 64 GiB restore cap can still exceed available disk. Restore also swaps files while other operations may be active; use a maintenance window until cross-operation coordination is added.
4. **Session lifecycle now has per-user token revocation; public shares still do not.** `app_users.session_version` is embedded in each signed session token (the `sv` claim) and re-checked on every request in `authService.sessionFromRequest`. `/auth/logout` advances the version, so a copied token stops validating immediately instead of lingering until its `exp`. Account deletion records the outgoing version in `app_user_readd_required`, and re-adding the user (`CreateUser`/`UpdateUserPermissions`) resumes one past it, so tokens that outlived the account never revalidate. Residual items: tokens minted before this change (`sv` absent, treated as `0`) are rejected once and users log in again; a cross-site `GET /auth/logout` can still force a logout of all of a victim's sessions (previously it forced only the browser cookie clear) — converting logout to a `CrossOriginProtection`-covered POST is a clean follow-up. Existing issued public shares have their own lifetime; removing their creator does not automatically revoke them.
5. **Proxy origin trust is not fully configured in application code.** Keep dynamic OAuth redirects off in production, preserve the public Host, overwrite forwarding headers at trusted ingress, and block direct untrusted access to the origin. Prefer a configured canonical public origin in a follow-up.
6. **Operational monitoring and update controls need review.** Edge rate limits, security event auditing, failed-auth visibility, alerting, backup encryption, secret rotation, and image/component scanning were not verified. The image downloads yt-dlp from a moving latest-release URL. Go's clean scan does not certify those artifacts.

## Rollout notes

Deploy the backend and frontend together; there has been no production deployment in this task. Replace example signing keys with random values of at least 32 characters. Anonymous local use now requires MEMEINDEX_ALLOW_ANONYMOUS=true and absent Discord settings; the README uses a loopback bind for this mode. Set MEMEINDEX_MAX_UPLOAD_BYTES if 256 MiB is too small for legitimate batches.

Existing valid backups exported by the app retain the expected column order. Hand-edited/reordered backups and noncanonical paths are rejected. Restores above the new expansion/entry limits are rejected. Uploaded playlists no longer produce previews; large/slow media processing can time out after 30 seconds. Standard MP4 behavior was verified, but unusual formats need a representative-media check.

Old reel history tokens are replaced on next navigation. OAuth logins spanning a restart must be restarted; replicas need sticky routing or shared single-use state. API clients without browser origin headers continue to work; browser clients on other origins are denied for unsafe methods. Purge existing cached share media after deploying the first-pass cache fix and verify a normal Discord login, uploads, previews, and sharing on the deployed build.

Implementation references: [Go cross-origin protection](https://pkg.go.dev/net/http#CrossOriginProtection) and [FFmpeg protocol restrictions](https://ffmpeg.org/ffmpeg-protocols.html).
